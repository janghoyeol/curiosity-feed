# 0003. 배치 수집 스케줄링 방식

## 상태

승인됨 (2026-10-28)

## 배경

ADR 0002에서 "배치 수집 스케줄링 방식(cron vs APScheduler)"을 미정으로 남겨뒀다.
이제 소스가 3개로 늘었고, 매일 자동으로 수집→Gate2 처리가 돌아가야 한다.

## 결정

- **APScheduler를 같은 FastAPI 프로세스 안에서** 돌린다. 별도 cron이나
  Docker 컨테이너를 추가하지 않는다 (가볍게 가자는 ADR 0002 방향 유지).
- `ENABLE_SCHEDULER=true` 환경변수로만 켜진다. 기본값은 꺼짐 — 테스트나
  일반 로컬 개발 중에는 스케줄러가 돌 필요가 없고, 매번 켜져 있으면
  의도치 않게 Groq/공공데이터 API를 호출하게 된다.
- 하루 한 번(UTC 18:00 = KST 새벽 3시) `run_daily_pipeline()`이 실행되고,
  소스별 수집 → Gate2 처리를 순서대로 한다.
- 소스 하나가 실패해도(API 키 만료, 네트워크 오류 등) 나머지 소스는
  계속 수집된다 (`run_ingestion`이 소스별로 예외를 잡아서 로그만 남김).
- Gate2는 작은 묶음(5개)으로 나눠서 묶음 사이에 5초씩 쉰다. Groq 무료
  티어의 TPM(분당 토큰) 한도를 실제로 여러 번 맞아봤기 때문에, 한 번에
  몰아서 처리하면 또 걸릴 게 뻔하다. 하루 최대 처리량(60개)도 캡을
  둔다.
- `process_pending_raw_materials`를 항목 단위로 즉시 커밋하도록 바꿨다
  (기존엔 배치 전체를 한 번에 커밋해서, 배치 중간에 LLM 호출 하나가
  실패하면 이미 성공한 항목들까지 전부 롤백됐었다). 실패한 항목은
  로그만 남기고 다음 항목으로 넘어간다.

## 알려진 한계

- 영구적으로 실패하는 원재료(예: LLM이 계속 이상한 응답을 주는 경우)가
  있으면 매일 다시 시도된다. 재시도 횟수를 추적해서 포기하는 로직은
  지금 단계에서는 만들지 않았다 — 실제로 그런 사례가 쌓이면 추가할 것.
- uvicorn을 멀티 워커로 띄우면 워커마다 스케줄러가 하나씩 생겨 같은
  작업이 중복 실행된다. 지금은 단일 워커로만 운영한다는 전제.
