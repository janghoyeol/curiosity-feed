# 0002. 기술 스택 및 Gate1/Gate2 설계

## 상태

승인됨 (2026-10-28)

## 결정

### 기술 스택

- **백엔드**: Python (FastAPI) 단일 서비스. 원재료 수집(배치)·API 서빙·LLM 호출을
  모두 한 서비스에서 처리한다. 이전 프로젝트처럼 Java(Spring)+Python을 나눌
  이유가 없다 — 상태 머신 같은 복잡한 도메인 로직이 없기 때문.
- **DB**: SQLite로 시작. SQLAlchemy로 접근해 나중에 Postgres로 교체하기 쉽게
  둔다. Docker/인프라 없이 로컬에서 바로 개발 가능.
- **프론트엔드**: 지금 당장 만들지 않는다. API가 안정된 뒤 붙인다.

### Gate 1 — 규칙 기반 중복/품질 필터 (LLM 호출 없음)

원재료를 가져올 때마다 다음만 체크한다:

1. `source + external_id` 조합이 이미 DB에 있으면 스킵 (완전 중복)
2. 본문 텍스트가 너무 짧거나(예: 10자 미만) 숫자/기호뿐이면 스킵

유사도 비교 등 복잡한 중복 탐지는 지금 단계에서는 생략한다 (오버엔지니어링).

### Gate 2 — 생성과 평가를 분리한 2단계 LLM 호출

이전 프로젝트에서 "분류용 단일 프롬프트가 너무 많은 일(분류+설명)을 하려다
애매한 결과를 내고, 동일 입력도 점수가 들쭉날쭉했던" 문제가 있었다. 이를
피하기 위해 역할을 분리한다:

1. **생성 단계**: 원재료 → "누구에게나 같은 답이 적용되는 보편적 사실형 질문"
   하나를 생성. 개인 상황에 의존하는 질문을 만들지 않도록 생성 단계의 프롬프트
   제약으로 강제한다.
2. **평가 단계**: 생성된 질문을 "오 궁금한데" vs "그래서 어쩌라고" few-shot
   기준(K5/아반떼 vs 엔진오일 예시)으로 점수화. 출력은 `{"score": float,
   "reason": string}` 형태의 JSON으로 강제해 판단 근거를 같이 받는다.
   temperature는 0.1~0.2로 낮춰 비결정성을 줄인다.

## 근거

- 각 프롬프트가 하나의 역할만 맡으면 둘 다 더 정확해진다.
- 생성 단계에서부터 "보편적 사실형"을 강제하면, 사용자가 쓴 질문을 분류할 때
  겪었던 "나 대신 선택해줘" 문제가 구조적으로 거의 발생하지 않는다.
- 구조화 출력 + 낮은 temperature는 이전 프로젝트에서 발견된 "동일 입력, 다른
  점수" 비결정성 문제를 완화하기 위한 선택.

## 미정

- LLM 제공자/모델 선택 (비용 대비 품질)
- 배치 수집 스케줄링 방식 (cron vs APScheduler)
- 평가 단계의 self-consistency(복수 샘플 평균) 도입 여부 — 비용 대비 효과를
  실측 후 결정
